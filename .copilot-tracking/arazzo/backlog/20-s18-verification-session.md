# S18 — Isolate a saga verification with a dedicated session

Part of [the epic](00-epic.md). **Consumer side, safety net of [S15](17-s15-verify-consumer.md).**

## Story

**As a** developer of an order saga service whose mocks return fixed ids, or whose steps do not all carry the order id,
**I want** to scope a verification to a session that my test opens and my service propagates,
**so that** the verification stays reliable when the correlation key alone cannot tell sagas apart.

## Domain examples

1. The mock example of `createOrder` returns the fixed id `o-42`. Two tests run in parallel, and both sagas carry `o-42`.
   - Without a session, verifying `o-42` is refused with *key o-42 shared by 2 saga instances*.
   - With sessions `t-1` and `t-2` in `x-microcks-session`, each verification sees only its own calls and passes.
2. The step `notifyCustomer` (`POST /notifications`) carries no order id. With session `t-1`, it is attached to the saga by the session and its order. Without a session, it is reported as not attached.
3. The service is instrumented with OpenTelemetry. The test asks for a verification on the trace id of its `traceparent`, without adding `x-microcks-session`, and only the calls of that trace are taken into account.
4. Inside session `t-1`, the test runs two sagas, `o-7f3c` and `o-91ab`, with keys generated by `uuid()`. Each verification by key, inside the session, sees only its saga.

## Acceptance criteria

**AC-01: A key shared by several sagas is reported, not mixed**
Given two sagas carrying the same order `o-42`, without a session
When the test asks to verify `placeOrderSaga` for `o-42`
Then the verification is refused, stating that `o-42` is shared by 2 saga instances

**AC-02: A session isolates parallel tests**
Given two tests propagating `x-microcks-session` = `t-1` and `t-2`, whose sagas both carry `o-42`
When the test of `t-1` asks to verify `placeOrderSaga` in session `t-1`
Then only the calls of session `t-1` are taken into account, and the verification passes

**AC-03: A step without a key is attached by the session**
Given the step `notifyCustomer` carries no order id, and the test propagates session `t-1`
When the test asks to verify `placeOrderSaga` in session `t-1`
Then `notifyCustomer` is matched at its place in the order

**AC-04: The trace id of `traceparent` can serve as a session**
Given an instrumented service whose calls carry the same `traceparent` trace id
When the test asks to verify `placeOrderSaga` for that trace id
Then only the calls of that trace are taken into account

## Technical notes

- The session value is free and chosen by the test (a UUID, for example). There is no session to open beforehand: Microcks groups the calls by the value of `x-microcks-session`, or by the trace id of `traceparent`.
- When session and correlation are both present, the session bounds the scope and the correlation separates the instances inside it.
- AsyncAPI, for later: `x-microcks-session` travels as a message header on Kafka, AMQP, NATS, SQS, SNS, Google Pub/Sub, IBM MQ and MQTT 5. MQTT 3.1.1 and WebSocket have no per-message headers, so they rely on correlation by a message field. Messages produced by an async trigger (`AsyncMockProducerTrigger`) carry over the session of the REST call that triggered them.
